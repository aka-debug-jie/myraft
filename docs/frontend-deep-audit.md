基线为 `05800e7128fa693141c2a6aba50fb4cdb98fa937`。本报告对应其上的修复，源码与测试程序摘要见 [source-manifest.json](../validation/frontend-audit-20261024/source-manifest.json)。测量完成时修复尚未提交或部署，清单中的 dirty 状态保留当时事实；随后按用户授权发布源码并更新只读预览，不回写历史测量。没有重新发布 Windows 包，用户未提交的设计文档不纳入发布。

本轮没有发现新的 P0/P1 缺陷。复现并修复了下面五项 P2 问题；这不是对所有故障条件的无缺陷证明。Raft、WAL、RPC 协议和持久化实现未修改。

## 已复现问题与修复

| 问题 | 触发与证据 | 最小修复 |
|---|---|---|
| 重连后操作一直禁用 | 控制器更换，SSE 间隔 100ms，配置请求耗时 250ms；每帧的新请求使前一响应失效 | `client.ts` 按控制器合并在途 bootstrap；旧控制器响应仍被丢弃，失败后允许后续帧重新读取 |
| 未决写入警告被无关操作清除 | generate 连接中断后，verify 即使返回 400，也会抹掉未知结果警告 | 将未决原因单独保留；普通错误和读操作结果不能清掉它。未知请求没有足够关联证据时保守保留至会话范围变化，不自动重发 |
| 完成任务被晚到 HTTP 回执复活 | SSE 已报告 succeeded，任务被后续 20 项挤出窗口，HTTP queued 才到达 | 只在当前 HTTP 请求存续期间记录已被 SSE 观察的 ID，拒绝旧 HTTP 状态回退；请求结束释放集合，不积累会话级无界历史 |
| 健康尾节点永久采样饥饿 | 前 32 个节点不回应、末尾节点健康；旧版连续 5 轮没有向健康节点发出有效 Status 请求 | `collector.go` 每轮轮转首批 8 个任务，保持结果数组与事件游标原顺序；预算耗尽时明确说明未尝试，不新增计数。新版第 2 轮采到健康节点 |
| 清理顺序阻塞后续终止 | FakeProcess 在首个 wait 时观察到只有第一个进程被 kill；kill 异常还会跳过相应 wait | `benchmark.py` 先向全部自有进程发 kill，再逐个 wait；失败保留句柄，其他进程继续清理。保留原有超时和 cleanup_unconfirmed 语义 |

前三项在两个渲染器中均有浏览器负例：基线 6/6 失败，修复后 6/6 通过。清理问题是机制级故障注入复现，**本轮没有观察到真实节点因此残留**。对应结果见 `recovery-before/`、`recovery-after/`、`client-before.txt`、`collector-before.txt` 和 `cleanup-before.txt`。

## 性能测量与有限优化

CPU profile 显示，带 source context 的 JSON reviver 是明显热点。现在先用原生 JSON 解码并检查整数范围；仅在出现不安全整数时，才从原始文本用原有 source reviver 重新解析。保留精确 int64、嵌套/负数/指数形式和不支持 source context 时的拒绝行为。NodeBadge 的入参均为基本类型，加入 `React.memo`，跳过无变化的徽标渲染；没有增加布局缓存或修改几何。

测量脚本也修复了三个缺口：分开记录导航至详情和点击至详情；将更新窗口的长任务与页面全程长任务区分；每次更新检查 Commit KPI 实际匹配，每次拖动检查视口确实移动。禁用 `__send` 的反例现在会被拒绝，不能再靠“不更新”取得漂亮数据。

同一 Linux 主机、Chromium、1440×900、正常动效；新旧版本使用相同修订后脚本，分别三轮。每轮 100 节点、120 次更新：

| 渲染器 | 原脚本 CPU/ms（三轮） | 修复后脚本 CPU/ms（三轮） | 均值变化 | 显示确认 P95/ms，原 → 新 |
|---|---|---|---|---|
| SVG | 1100.8 / 1111.4 / 1084.8 | 562.0 / 561.8 / 555.5 | −49.1% | 32.3 / 32.2 / 32.3 → 32.3 / 32.2 / 32.2 |
| Flow | 1856.0 / 1859.8 / 1829.3 | 1696.6 / 1656.6 / 1671.2 | −9.4% | 33.6 / 32.9 / 32.5 → 32.5 / 32.7 / 32.8 |

更新窗口没有记录到长任务，拖动及更新内容检查通过，没有触发多数轮次 P95 退化超过 20% 的门槛。表中 CPU 使用 CDP `ScriptDuration` 差值表示主线程脚本执行成本，不是操作系统进程 CPU 占用率，包含两版相同的合成数据构造开销。显示确认包含两次 RAF，明显受屏幕帧节拍影响；CPU 降幅**不等于**页面响应或 Raft 吞吐提升。11 节点和拖动指标也保留在原始结果中。

代价没有隐藏：Node 24 微基准，约 48KB 的 100 节点帧，三轮、每轮 250 次，安全整数场景解码均值从 340.7ms 降至 47.7ms；含超大整数场景因二次解析从 346.0ms 增至 392.0ms（约 +13.3%）。原文精度优先于该少见分支的速度。不能把微基准收益直接推广到所有真实集群。

## 资源与真实流程

- 每种渲染器 500 次手机详情开关：SVG 在第 50→500 次保持 DOM 352、监听器 348；Flow 保持 DOM 418、监听器 395；SSE 始终 1。GC 后堆分别增长约 0.53MB、0.69MB，不能称为零增长或长期零泄漏认证。
- 独立真实 11/100 节点 × SVG/Flow 四组均通过：创建、2101 命令、完整校验、检查点、停止 Leader、重选、再提交 3 条、原盘恢复、历史校验、导出。222 个节点通过独立算术参考，最终各 2104 条算术命令；全部自有监听端口清理完成。
- 1/5/10 浏览器各跨 3 轮采集，11 节点均为 33 次、100 节点均为 300 次监控调用尝试，没有按浏览器倍增。计数不是节点实际收包数，也不是 Raft 通信吞吐。
- 100 节点、20 次 Leader 停止/恢复、180 秒的独立诊断重跑通过，已提交历史检查持续通过；采样中复制 worker/入站连接均为 99，停止后 goroutine 从 2 回到 2。它覆盖的是停止并重启 Leader，不代表所有存活节点连续降级场景或长时压力均已认证。

首次额外 soak **失败过一次**：原节点重新绑定端口 39987 时 EADDRINUSE。交叉核查发现，并行的 100 节点 UI 验收在重叠时间窗口已启动使用该端口的 Node 3；配置、日志、创建回执相互吻合，证据强烈支持独立实验之间的端口竞争。没有当时的 socket/PID 快照，日志 mtime 也不是 bind 的精确时刻。原 FAIL 与隔离后的 PASS 均保留在证据中，没有增加睡眠或放宽断言。今后包含停机再恢复的动态端口实验应串行运行，或预先使用互不重叠的固定端口配置。

## 剩余边界与下一步

1. 公平轮询消除了固定顺序永久饥饿，2 秒预算下仍可能有当轮未采样节点；不得将全部可达当成共识健康证明。
2. 取消已向全部自有进程发出 kill，仍不能保证操作系统在 15 秒内完成全部退出；清理失败必须继续可见。
3. Flow 的节点包装与全量数据更新仍有 CPU 成本。本轮收益低于 SVG，继续保留 SVG 为主版本；更细的 Flow 数据复用应独立测量，避免以复杂缓存破坏状态更新。
4. 目前无新增 P0/P1 的实证，但测试是有限场景。事件环可能明确报告缺口；这与 WAL/已提交日志丢失不是同一事实。

复现入口：`npm --prefix frontend test`、`npm --prefix frontend run build`、`go test -count=1 ./...`、`go test -race -count=1 ./...`、`python -m unittest discover -s scripts -p 'test_*.py'`。独立测试服务上运行 `scripts/audit_recovery_ui_test.py`、`scripts/phase234_performance.py` 的 `--url` 与新的 `--output`。真实流程使用 `scripts/prototype_acceptance.py`；长资源检查见 `raft/soak_test.go` 的环境变量说明，避免与新建集群实验并行。
